# Figmaレビュー基準（実装観点）

## 一言でいうと
Figmaデータを「きれいな見た目」ではなく **実装仕様（HTML/CSS/JS/CMS）を読み取れる設計データ** として評価するための基準。コーディング着手前のレビューで、実装者の推測・確認戻しを減らすことが目的。

## なぜ重要か
WordPress / Web制作では、Figmaの曖昧さがそのまま実装の確認戻し・属人的判断・保守性低下に直結する。この基準でレビューすれば、「デザイン会社へ確認すべき点」「実装側で吸収してよい点」「実装前に確定が必要な点」を切り分けられる。

## 判定ランク（4段階）
> [!info] 各項目をこの4段階で判定する
> - **OK** … 実装に必要な情報が読み取れる → そのまま実装に進みやすい
> - **要確認** … 見た目はあるが意図・ルールが不明 → デザイン会社/クライアント確認が必要
> - **要整理** … 共通化・命名・構造が不足 → Figma修正または実装側判断が必要
> - **対象外** … 今回の実装対象ではない → 明示する

## 優先度の考え方
- **A（着手前に必須）**：レスポンシブ / コンポーネント / リンク範囲 / 文字・余白ルール
- **B（品質・共通化）**：画像比率 / アイコン / カラー / シャドウ / 角丸
- **C（保守性・効率）**：レイヤー名 / バリアント名 / 細かな数値整理

## 特に見落としやすい点
- **見た目が同じでも別仕様**：外部リンク/アンカー、カード全体リンク/ボタンのみ、disabled/通常グレー、トップ用/下層用フッター。見た目だけで統合しない。
- **Figmaのpx値をそのまま使わない**：13/21px の端数、15.5px の小数、15/16/17px の揺れ、固定px の line-height・letter-spacing は共通値へ丸める判断が要る（意図があれば個別指定）。
- **SPデザインがないと実装者判断が増える**：要素順・表示非表示・縦積み切替・トリミング・CTA位置・メニュー開閉・列数など。
- **CMS可変箇所はFigmaの見た目だけでは不足**：文字長短・画像なし・タグ複数・リンク未設定・0件・終了/非公開/満席などの状態差分。

## 最も重要な結論
Figmaが完成していても、次が不明だと実装で確認戻しが増える：
1. PC/SP の変化 2. 共通部品と個別部品の区別 3. クリック範囲 4. 状態差分 5. 余白・文字・色の共通ルール 6. CMS更新時の表示ルール 7. 画像・アイコン素材の扱い 8. 確定/未確定デザインの区別
