# 02. デザイントークンのマッピング（Q-02）

- 設問: デザイントークン（色・タイポ・spacing変数）をコードにどうマッピングするか？
- 状態: 合格（kazu の確定承認待ち。批評記録は STATE.md [6]）

## 方針

Figma Variables / Styles は**単一の機械的な変換規則**で CSS カスタムプロパティへ写像する。変換の入力は Q-01 の手順で取得した出典タグ付きの値（`variable_defs`）に限定し、トークンの新設・改名・値の丸めをエージェント判断で行わない（トークンの正はデザイン側にある）。

根拠の凡例は Q-01（spec/01-extraction.md）と同じ:【公式】【実測:MyBrain】【実測:スキーマ】【仮説】

## 1. 入力の形（何が取得できるか）

- `get_variable_defs` が返すのは「**変数名 → 解決済みの値**」のフラットな対応表（例: `icon/default/secondary: #949494`）【実測:スキーマ】。変数の型・コレクション構造・エイリアス関係は返らない。
- パラメータは `nodeId` / `fileKey` のみで、**モード（ライト/ダーク等）を指定する手段が無い**【実測:スキーマ】。返った値がどのモードで解決されたかも出力からは判別できない。したがって**モード別値の取得は本ツール単独では不可**。
  - 代替手順（非Enterprise案件）: モードごとの代表フレーム（例: ライト用トップとダーク用トップ）が存在する場合、それぞれのノードで `get_variable_defs` を呼び、同名変数の値を突き合わせてモード別対応表を作る。モード別フレームが無い場合は「モード未取得」としてデザイナー確認に回す。
  - 補完手段（Enterprise案件のみ）: REST Variables API（`GET /v1/files/:key/variables/local`）【公式・出典1】。モード別値を含む完全な定義が返るかは本ループでは**未検証**【仮説】。使用する案件で最初に実測してから頼る。
- Styles（Variables 化されていない色スタイル・テキストスタイル）も `get_variable_defs` の返却対象【公式・出典2】であり、本仕様では Variables と同じ規則で変換する。

## 2. 変換規則（Figma → CSS カスタムプロパティ）

以下は本仕様の規定（取り決めであり、出典を要しない設計判断。採用は kazu の確定に含まれる）。

### 2-1. 名前

- Figma の変数パス `group/sub/name` → `--group-sub-name`。
- 正規化: 小文字化、`/`・空白・`_` → `-`、連続する `-` は1つに統合。
- 非ASCII名（日本語の変数名等）は自動翻字しない。案件側 `MyBrain/rules/` に英名対応表を作り、対応表が無い変数は「未変換」としてエスカレーションする。
- 正規化後に名前が衝突した場合は自動リネームせず停止し、衝突一覧を報告する。

### 2-2. 値

| Figma側の型 | 変換 | 根拠 |
|---|---|---|
| color | 解決済み値（hex / rgba）をそのまま転記。近似色への丸め・再計算をしない | 本仕様の規定 |
| number（spacing・radius等） | px を基本とする。rem 等への換算規約が案件側にある場合は案件側 `MyBrain/rules/units.md` を優先。border・罫線・線状の要素は常に px | 【実測:MyBrain corrections.md 2026-07-07（線はpx）】 |
| typography（テキストスタイル） | `font-family` / `font-size` / `font-weight` / `line-height` / `letter-spacing` の個別プロパティへ展開。line-height は単位なし比率へ換算、letter-spacing は px→em 換算（式は 2-2-1） | 【実測:MyBrain corrections.md 2026-07-06（line-height単位なし）、mistakes.md 2026-06-25（letter-spacing px→em）】 |

### 2-2-1. タイポグラフィ換算式（本仕様の規定）

- `line-height`（単位なし比率）= lineHeightPx ÷ fontSizePx。小数第3位まで（四捨五入）。Figma側が % で返す場合は % ÷ 100。
- `letter-spacing`（em）= letterSpacingPx ÷ fontSizePx。小数第3位まで（四捨五入）。Figma側が % で返す場合は % ÷ 100 を em 値とする。
- **fontSizePx が未取得の要素では換算しない**。換算元が揃うまで「未確認」として停止する（Q-01 §3 の inferred 禁止ルールに従う。fontSize を推測して換算した値は検証基準に使えない）。

### 2-3. 配置

- 変換したトークンは `:root {}` に一元定義する。コンポーネント内での再定義（同名カスタムプロパティのシャドーイング)を既定では行わない。
- モードがある場合は `:root[data-theme="<mode>"] {}` で上書きし、既定モードの値を `:root` に置く。既定モードがどれかはデザイナー確認事項（機械的に判別できないため）。

## 3. トークン化されていない生値（ハードコード値）の扱い

### 3-1. 検出

- `get_design_context` の出力で、トークン名（変数名）が付かずに現れた値（例: `#1A1A1A`、`text-[40px]`）を「生値」として抽出する。
- 照合の前に、両辺（生値・トークン値）を次の規則で正規化する（本仕様の規定）:
  - 色: 小文字の16進表記へ統一。3/4桁は6/8桁へ展開（`#fff`→`#ffffff`）。`rgb()`/`rgba()` は16進へ変換し、alpha=1 は6桁にする。
  - 数値: 単位付きpx表記へ統一（`0`→`0px`）。小数は末尾のゼロを除去（`16.50px`→`16.5px`）。
  - `%`・`em` 等 px 以外の単位はこの正規化の対象外とし、単位が一致する場合のみ照合する。
- 正規化後の値を §1 の対応表と照合する。照合は**値の完全一致のみ**。±数px・近似色などの「近い」一致でトークンへ丸めることを禁止する（Figma側の意図的な例外値を潰すため。丸め禁止は本仕様の規定）。

### 3-2. 扱いの規則

1. 対応表に**完全一致**するトークンがある → そのカスタムプロパティを参照する（生値のままコードに書かない）。
2. 一致が無い → 使用箇所のコンポーネントスコープにローカル値として書き、`raw`（未トークン値）として一覧に記録する。**新トークンの自動発行・命名はしない**。
3. 同一の `raw` 値が複数箇所（目安3箇所以上。閾値は【仮説】であり運用で調整）に再出現 → 「トークン化候補」としてデザイナー確認リストに起票する。変数化するかの判断はデザイン側。

### 3-3. 記録

- `raw` 一覧は検証用 spec ファイル内で、推測値の隔離枠 `inferred`（Q-01 §3）とは**別枠**として持つ。`raw` は「Figmaから取得した実値だがトークン未割当」、`inferred` は「出典の無い推測値」であり混同しない。
- `raw` の各行には取得元ノードIDと出典タグを付け、Q-09（自動検証）の照合対象に含める。
