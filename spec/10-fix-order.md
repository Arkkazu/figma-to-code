# 10. 検出した差分の修正順序（Q-10）

- 設問: 検出した差分をどの順で修正するか？
- 状態: 確定（2026-07-30 オーナー承認）。§1-2 は [79] の独立批評で不合格となった R3 付与条件を **P-7 として是正起草済み（2026-07-30、STATE.md [81]）。独立批評（codex）待ち**。批評記録は STATE.md [26][79][80][81]

## 方針

Q-09 の検証で検出した FAIL は、**依存関係の上流（構造）から下流（装飾）へ**の固定順で修正する。1回の修正は「1原因・1プロパティ」に限定し、修正のたびに対象範囲の照合を再実行する。順序の目的は手戻り最小化: 上流カテゴリの修正は下流カテゴリの実測値を変えるが、逆方向の影響は無い（または限定的）ため、下流から直すと上流修正後にやり直しになる。

根拠の凡例は Q-01 と同じ:【公式】【実測:MyBrain】【実測:スキーマ】【仮説】

## 1. 差分カテゴリの優先順位

| 順位 | カテゴリ | 含まれる差分 |
|---|---|---|
| 1 | DOM構造 | 要素の欠落・余計な要素・順序違い（全件対応表の不一致【実測:MyBrain pipeline】） |
| 2 | レイアウトモードとカスケード | display / flex-direction / grid / order / position、修飾クラスの有無、共通CSS・カスケードレイヤーによる上書き |
| 3 | 親要素の寸法・余白 | 親の width / height / padding / gap / margin |
| 4 | 子要素の寸法・余白とレイアウトに影響するタイポ | 子の width / height / margin、font-size / line-height / letter-spacing（行ボックスと折返し幅に影響するため寸法系として扱う）。修正後に改行位置・行数を再検証 |
| 5 | 色・背景・画像・CSS合成 | color / background / 画像内容 / opacity / blend mode（ボックス寸法に影響しない） |
| 6 | 細部装飾 | 角丸・影・線・アイコン形状・グラデーション |
| 7 | 状態・モーション | hover / open / closed / 中間状態、duration / easing（静的差分がすべて解消してから） |

- **機械実行規約**: 検出した FAIL 一覧に本表のカテゴリ番号を付与し、**カテゴリ番号の昇順にソートして先頭から処理**する。同一カテゴリ内は §2-2 の「共通原因で解消できる FAIL 数が多いもの」を先にする。
- 設問文（QUESTIONS.md）の例示「レイアウト→サイズ→色→タイポ→細部」との対応: レイアウト = 1・2、サイズ = 3・4（親→子）、タイポ = 4 のタイポ寸法系（レイアウトに影響するため「サイズ」と同段に統合）、色 = 5、細部 = 6・7。

### 順序の根拠（手戻り最小化）

- **1 → 2**: DOM 構造が違えばセレクタもレイアウト前提も崩れ、以降のすべての実測が無効になる。構造確定が最初【実測:MyBrain corrections.md 2026-07-01 の確認順 1-2】。
- **2 → 3 → 4**: 親のレイアウトモード・gap が直ると、子要素の座標 FAIL がまとめて消える。実例: SP カードの縦余白ズレで、親の `gap` と `display: contents` を確認せず細部 gap だけ直して手戻りした【実測:MyBrain mistakes.md 2026-07-02】。逆に子から直すと、親修正後に子の再修正が必要になる。
- **4 の位置づけ**: font-size / line-height / letter-spacing は行ボックスの高さ・折返し幅を変えるため「色より前・親寸法より後」。実例: FV 実績サマリーのズレは細部の font-size ではなく `padding-top` が原因で、寸法系の切り分けを先にすべきだった【実測:MyBrain mistakes.md 2026-07-01】。
- **5 以降が後**: 色・合成・装飾はボックス寸法に影響せず、いつ直しても他の実測値を変えない。
- **7 が最後**: 状態・モーションの spec 値は静的レイアウトの上に定義されるため、静的差分が残った状態で調整すると基準が動く。

## 1-2. 修正経路（ルーティング）ラベル

> 状態: **起草（独立批評待ち）**。2026-07-28 にオーナー指示で追加。Q-10 の設問状態は変更していない。

目的は、差分を検出した時点で「どこまで戻すか」を一意に決めることにある。§1 のカテゴリは**直す順序**を決めるが、戻り先は決めない。経路ラベルは**戻り先と禁止事項**を決める。FAIL 1件ごとに、カテゴリ番号と経路ラベルの両方を付与する。

| ラベル | 付与条件 | 戻り先（この工程からやり直す） | この経路で禁止すること | 再実行の範囲 |
|---|---|---|---|---|
| **R1 再取得** | Q-09 の `SPEC FAIL`。Figma値・asset・対応node・DOM対応表が未取得／矛盾／証跡不足【実測:MyBrain pipeline 3A-3】 | フェーズ1（取得・spec更新）。`preflight` の凍結入力から取り直す | 実装ファイルの変更、未取得値の推測補完、目視での代替 | 集約specを更新後、同一の全件コマンドを最初から1回 |
| **R2 構造** | §1 カテゴリ1、およびフェーズ3B 1-0 の構造一致ゲート違反（FigmaのAuto LayoutグループとHTMLの親子構造の不一致）【実測:MyBrain pipeline 3B 1-0】 | HTML/PHPテンプレートの構造修正 | 親の一律 `gap`・子の負 `margin`・要素別の打消しで視覚だけ合わせること、CSSからの着手 | 構造修正後に同一checkpointを全件1回。HTML/PHPを変更したためW3Cを1回 |
| **R4 要判断** | `LAYOUT FAIL` / `VISUAL FAIL` / 未分類差分のうち、下記6条件のいずれかが**観測された**もの（下記 R4-1〜R4-6） | オーナー確認（実装を進めない） | 独自解釈での実装続行、スコープの黙示的拡張、「大体合っている」での通過 | 判断が返るまで対象checkpointを停止し、報告とSTATEへ未確認として残す |
| **R3 局所** | **残余**。R1・R2・R4 のいずれの条件にも一致しない `LAYOUT FAIL` / `VISUAL FAIL`。原因の所在を判定者が推定して付与するのではなく、上位3ラベルの否定として決まる | 対象SCSS／該当セレクタ／該当assetのみ | 1要素ずつ直して撮り直す往復、対象スコープ外への横展開 | 同一checkpointのFAILを1つの修正バッチへ集約し、全件コマンドを1回 |

#### 判定順序（機械判定。上から順に評価し、最初に一致したラベルを採用する）

ラベルは Q-09 の全件検証が出力した分類と、preflightで凍結済みの証跡だけから決める。判定者が原因を推定して選ばない。

1. **R1** ← 分類が `SPEC FAIL`（フェーズ3A-2 の定義: Figma値・asset・対応node・DOM対応が未取得／矛盾／証跡不足）。
2. **R2** ← `LAYOUT FAIL` / `VISUAL FAIL` のうち、次のいずれかが記録されているもの。(a) フェーズ3B 1-0 の構造一致ゲート違反（FigmaのAuto LayoutグループとHTML親子構造の不一致）(b) §1 カテゴリ1（全件対応表のDOM構造不一致・要素の欠落・余計な要素・順序違い）(c) component manifest の `spacingOwnership` 違反。
3. **R4** ← 次のいずれかが**観測された**もの。観測できる事実だけを条件とし、原因の推測を含めない。
   - **R4-1**: FAIL が3A-2 の3分類に入らない未分類差分である。
   - **R4-2**: component decision manifest の該当componentの判定が `new` である（独立承認が必要）。
   - **R4-3**: 解消に、scope lock（D-012）の許可パス外にあるファイルの変更が必要と判明した。
   - **R4-4**: 必要な換算が案件側 `MyBrain/rules/units.md` の換算表に該当しない。
   - **R4-5**: 対象nodeについて、Figmaデータ自体の矛盾がspecのnoteに記録されている（例: component固定高さと中身合計の不一致）。
   - **R4-6**: オーナー訂正に起因するscopeで、訂正受領証（correction receipt）が未取得または失効している。
4. **R3** ← 上記1〜3のいずれにも一致しない `LAYOUT FAIL` / `VISUAL FAIL`（残余）。

この順序により、1件のFAILに付与されるラベルは常に1つに決まる。R3 と R4 の境界は「R4-1〜R4-6 が観測されたか」だけで決まり、判定者の解釈を含まない。

- **併記**: FAIL一覧には `C4/R3` のようにカテゴリ番号と経路ラベルを併記する。処理順は §1 のカテゴリ昇順を維持し、同一カテゴリ内は戻り先が上流のものから閉じる（R1 → R2 → R3）。
- **R4 はカテゴリ順の対象外**: R4 は §1 のカテゴリ昇順処理に載せない。カテゴリ番号に関係なく、検出した時点で対象checkpointを停止してオーナーへ上げる（カテゴリ順に並べて後回しにしない）。したがって §1 のカテゴリ昇順と §1-2 の判定順序は競合しない。カテゴリ昇順が支配するのは R1〜R3 の処理順だけである。
- **上流優先**: 1件のFAILに複数のラベルが当てはまる場合は、より上流のラベルを採用する（R1 > R2 > R3）。下流ラベルとして処理して通過させない。
- **不変**: ラベルは検出時に付け、修正の途中で読み替えない。R1 を R3 として実装側で吸収する、R2 を R3 の余白調整で見た目だけ合わせる、はいずれも禁止する。
- **R3 → R4 のエスカレーション（読み替えではない）**: R3 として着手した後に R4-1〜R4-6 のいずれかを観測した場合は、ラベルを書き換えるのではなく **R4 へエスカレーションした事実を追記**し、対象checkpointを停止してオーナー確認へ回す。元のR3ラベルと、観測したR4条件の番号・根拠・観測時刻を両方残す。これは D-012 のscope lockが対象外パスの検知でscopeを `blocked` にする挙動と同じ扱いであり、上流方向への移動だけを許す（R4 から R3 への差し戻しは禁止）。
- **ラベル付けの単位**: Q-09 の全件検証が出力する `SPEC FAIL` / `LAYOUT FAIL` / `VISUAL FAIL` の各行に付与する。検証ツールの分類を人が上書きしない。分類できないFAILは未分類差分として R4 とする。

### 未収束の宣言（3ラウンド）

§2-5 の停止条件を、報告の形式まで固定したもの。

- **FAILキーの定義**: 未収束の判定単位は `viewport` / `対象セレクタ` / `測定項目`（Q-09 の全件検証が出力するFAIL行の識別子。`verify-layout` の出力ラベルは「セレクタ＋測定項目」で、viewportは実行単位で分かれる）の3つ組とする。参考情報として Figma node ID・カテゴリ番号・経路ラベルを併記するが、同一性の判定には使わない。
- 同一checkpointで、**同一FAILキーが3ラウンド連続でPASSしない**場合、修正を続けずに「未収束」を宣言する。ラウンドはフェーズ3B「FAIL時の反復」の1回（一括修正＋同一条件での全件再実行）を1ラウンドとして数える。件数の増減や別FAILキーのPASSは、当該FAILキーのラウンド数をリセットしない。
- 未収束の報告には次の4点を必ず含める。
  1. 残っているFAILのカテゴリ番号・経路ラベル・件数
  2. 実施した3ラウンドの修正内容と、各ラウンドの実測差分（推移がわかる形で）
  3. 原因の候補（確定していないことを明示する。断定しない）
  4. **オーナーが選べる選択肢**と、それぞれの影響範囲（例: Figma値を採用／実装側の既存共通値を採用／対象を別スコープへ分離）
- 未収束の宣言は**失敗の報告であって、合否の緩和ではない**。宣言後に spec の許容誤差を広げる、対象要素を spec から外す、PASS済みだけを再測定して通す、のいずれも禁止する。

## 2. 修正の実行規則

1. **診断表を先に埋める**: コード変更前に、共通Vault `rules/corrections.md`（2026-07-01）の診断表（対象 / Figmaノード / 現DOM / 現CSS / display・grid・flex・order・modifier・cascade / ズレ方向 / 原因確定 / 変更する1プロパティ / 変更しないプロパティ）を埋める。**埋められない場合はコードを触らない**【実測:MyBrain】。
2. **1修正 = 1原因・1プロパティ**。複数 FAIL に共通する原因があれば、それを1つの修正として扱ってよい（例: 親の gap 1箇所で子の座標 FAIL 5件が解消）。
3. **修正ごとに再照合**: 対象セクションの verify（Q-09 層2）を再実行し、①対象 FAIL の解消 ②新規 FAIL の発生なし の両方を確認してから次の差分へ進む。
4. **下流の先行修正の禁止**: 上位カテゴリに FAIL が残る間は、下位カテゴリの差分値を「確定した差分」として扱わない（上流修正で変わり得るため）。
5. **行き詰まり時のリセット**: 同一 FAIL に対する修正が2回失敗したら、原因の決めつけを疑い診断表を作り直す。3回失敗したら作業を止めて差分内容を報告する（原因を推測で連打しない【実測:MyBrain corrections.md 2026-07-01 / mistakes.md 2026-07-01】。ループ全体の停止条件は Q-12）。

## 3. 合否基準との対応

- 差分カテゴリの優先順位: §1 の表（レイアウト構造 → 寸法 → タイポ寸法系 → 色 → 細部 → 状態）
- 順序の根拠（手戻り最小化）: §1「順序の根拠」（依存関係の方向と MyBrain 実例2件）
- 経路ラベルの検証可能性: §1-2「判定順序」は、Q-09 の出力分類（`SPEC` / `LAYOUT` / `VISUAL` / 未分類）、フェーズ3B 1-0 の構造一致ゲート、component manifest の `spacingOwnership`、component decision の `new` 判定、scope lock の許可パス、案件側 `units.md` の換算表、specのnote、訂正受領証という**すべて観測可能な入力**から上位優先で決まる。R3 は上位3ラベルの否定（残余）として定義されるため、1件のFAILに対するラベルは一意に決まり、判定者の解釈を含まない。ラベルの妥当性は「FAIL一覧の全行にカテゴリ番号と経路ラベルが付いているか」「R1 のFAILに対して実装ファイルが変更されていないか」「R4 の各行に R4-1〜R4-6 のいずれかの観測根拠が記録されているか」で検査できる
- 未収束の検証可能性: §1-2 の宣言条件は「同一checkpoint・**同一FAILキー**（viewport／セレクタ／測定項目）で3ラウンド連続PASSなし」であり、checkpointの実行記録から機械的に判定できる
- （補足）実行規則: §2
