# 13. アクセシビリティの実装と検証（Q-13）

- 設問: アクセシビリティ（セマンティクス・ARIA・キーボード・コントラスト）をどう実装・検証するか？
- 状態: 合格（kazu の確定承認待ち。批評記録は STATE.md [34][38]）

## 方針

アクセシビリティは Figma が正解を持たない領域（意味・代替テキスト・操作）を実装側が補うため、**Figma照合（Q-09）とは別の合格軸**として扱う。参照規格は WCAG 2.1 の AA 該当基準（出典1）とするが、本仕様が合格判定に使うのは §1 の表に列挙した項目に限る（サイト全体の AA 適合を宣言するものではない。適合宣言が必要な案件は kazu と範囲を別途合意する）。

計測可能なものは機械検証（ツール・数値閾値）で判定し、意味・文言・操作感の妥当性は人間レビューで判定する。

根拠の凡例は Q-01 と同じ:【公式】【実測:MyBrain】【実測:スキーマ】【仮説】

## 2. Figmaデザインとコントラスト基準が矛盾する場合

- デザイン実値が §1 の閾値を満たさない場合、**エージェントは色を変えない**（Figma 実値が正。Q-02 §3-1 の丸め禁止と同じ原則）。
- 該当箇所を「コントラスト未達リスト」（要素・実測比・必要比・該当基準）としてデザイナー/kazu に報告し、判断（デザイン側で色変更 / そのまま許容）を検証 spec の note に記録する。
- 記録済みの許容判断がある項目は、機械検証で「報告済み例外」として PASS 扱いにする（未報告の未達は FAIL のまま）。

## 3. 検証手順（機械検証の実装）

1. **W3C**: `C:\AI\web-development\rules\w3c-validation.md` を適用する。合格基準・実行手順・未確認時の扱いは同ファイルを正本とし、HTML確定時に実行する。
2. **axe-core**: CDP / Playwright でページに axe-core を注入し、WCAG A・AA タグのルールを実行。violations 0 を PASS 条件とする。ルールの除外は行わない（除外が必要な場合は理由と対象を spec の note に記録し kazu の承認を得る）。
3. **コントラスト**: Q-09 層2 の computed style 取得時に、テキスト要素の `color` と実効背景色を採り、WCAG 相対輝度式で比を算出。§1 の閾値で判定。**機械/人間の判定境界（§1 と共通の単一規則）**:
   - **機械判定の対象**: 実効背景が**単色に解決できる**要素。すなわち ①祖先を遡って最初に見つかる不透明の `background-color` が背景である ②途中に半透明の `background-color` がある場合は、その下が単色であればアルファ合成した色を背景として使う。
   - **CSS `opacity`を含む実効色**: CSS `opacity`が1未満の対象または祖先を持つ場合、対象の前景色と背景色の各合成層を描画groupとして、各祖先の`opacity`を順に乗算し、下層の単色背景へalpha合成した実効前景色・実効背景色でWCAG比を計算する。下層まで単色に解決できない場合は、比を推測せず「コントラスト人間判定リスト」へ送る。
   - **機械判定から除外し人間レビューへ回す**: 判定領域の背景に `background-image`（画像・グラデーション）・`blend mode`・`<img>`/`<video>` 等の描画要素が重なる場合、または半透明の下が単色に解決できない場合。除外した要素は「コントラスト人間判定リスト」（要素・除外理由）として出力する。
4. **キーボード走査**: スクリプトで `Tab` 送りを行い、以下の定義で判定する。開閉 UI は開・閉の両状態で走査する（Q-08 §1-3）。
   - **対象集合（フォーカス可能要素）**: `a[href]`・`button`・`input`・`select`・`textarea`・`summary`・`[tabindex]`（値 0 以上）・`[contenteditable="true"]`、および `audio[controls]` / `video[controls]` / `iframe`。
   - **除外条件**: `disabled` / `[tabindex="-1"]` / `aria-hidden="true"` の要素とその子孫 / `display: none`・`visibility: hidden` で不可視 / 閉状態の開閉 UI 内部（閉状態の走査では非対象、開状態の走査で対象）。
   - **判定**: ①対象集合の全要素に Tab で到達できる（除外条件該当を除く）②フォーカス順が DOM 順と一致 ③モーダル open 中のフォーカストラップと Esc 動作 ④フォーカス可視。
   - **フォーカス可視の判定式**: 各対象要素について、非フォーカス時とフォーカス時（`:focus-visible` 相当をキーボード操作で発生させる）の computed style を比較し、(a) `outline-style` が `none` 以外かつ `outline-width` > 0、**または** (b) `box-shadow` / `border-*` / `background-color` のいずれかに視覚差分がある、のどちらかを満たせば可視と判定する。**差分が1つも無い要素 = FAIL**（0件で PASS）。

## 4. 実装規則（既定）

### 4-1. セマンティクス

- 操作要素は `button` / `a[href]` を使う。`div` + click ハンドラーによる疑似ボタンを禁止する（2.1.1 Keyboard【公式・出典1】をHTML標準で満たすため）。
- 不正なネスト、フォームの `label`、見出し階層などのHTML実装規則は `C:\AI\web-development\rules\w3c-validation.md` を適用する。
- ARIAの実装規則は `C:\AI\web-development\rules\w3c-validation.md` を適用する。

### 4-2. alt の分類規則（Figma からは判別できないため実装側で決める）

- **意味のある画像**（テキストを含む画像・情報を伝える図・リンクになっている画像）→ 内容・役割を表す alt を書く。
- 画像の `alt` は `C:\AI\web-development\rules\w3c-validation.md` の実装規則を適用し、Figmaでは装飾か意味を持つかの分類だけをここで決める。
- 分類に迷う画像はデザイナー確認リストへ起票し、確認までは「意味のある画像」側で暫定実装する（情報の取りこぼし防止。本仕様の規定）。

### 4-3. 状態・操作

- 開閉 UI: `aria-expanded`（必要に応じ `aria-controls`）を付与し、JS で状態と同期する【実測:web-development corrections.md 2026-07-07】。
- モーダル: `role="dialog"` + `aria-modal="true"`、開いたらフォーカスをモーダル内へ、閉じたら起動要素へ戻す（本仕様の規定）。
- フォーカス表示: `outline: none` 単独指定を禁止し、消す場合は `:focus-visible` の代替スタイルを必ず用意する（Q-08 §2-2 継承）。
- `prefers-reduced-motion: reduce` の尊重は Q-08 §2-4 に従う。
