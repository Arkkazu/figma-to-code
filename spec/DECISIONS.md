# DECISIONS: figma-to-code 設計判断

このファイルには、Figma実装プレイブックの運用方針だけを記録する。案件固有の判断は案件側 `MyBrain/` と `STATE.md` に置く。

## D-01: Figma MCPを一次取得手段にする

- 状態: 採用
- 判断: Figmaノード、デザインコンテキスト、変数、スクリーンショットの取得はFigma MCPを一次手段とする。
- 理由: 実装エージェントが対象nodeを直接取得し、URL・node-id・可視レイヤーを証跡化できるため。
- 補足: MCPで取得不能な情報だけを、明示した補助手段で補う。推測で補完しない。

## D-02: コンポーネント単位でcheckpointを通す

- 状態: 採用
- 判断: 変更したコンポーネントごとに、CDP実測と必要な画像差分をPASSさせる。
- 理由: ページ末尾まで実装してから大きな差分を発見することを防ぐため。

## D-03: L1とL2を分ける

- 状態: 採用
- 判断: L1ではコードを編集せず、Figma取得・spec・DOM対応表・page coverage・差分レポートを準備する。オーナー承認後にL2へ進む。
- 理由: 対象範囲の取り違え、未取得要素、検索・絞り込みUIなどの実装漏れを編集前に検出するため。

## D-04: page coverageでページ全体を管理する

- 状態: 採用
- 判断: PC/SPページ全体の全セクションをtarget/contextとして登録し、targetを順番にverifiedへ進める。
- 理由: 指定範囲だけを見て、ページに存在する要素やセクションを取りこぼすことを防ぐため。

## D-05: Figma gateをGit hookへ結び付けない

- 状態: 採用
- 日付: 2026-07-17
- 判断: Figma照合はコーディング反復の中で実行し、commit、push、deployには実行しない。
- 理由: 実装時に必要な設計・実測検証と、変更を履歴・検証環境へ反映する操作は別の責務であるため。
