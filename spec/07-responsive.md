# 07. 固定カンバスから可変ビューポートへの解釈（Q-07）

- 設問: 固定カンバスのデザインを可変ビューポートへどう解釈するか？
- 状態: 合格（kazu の確定承認待ち。批評記録は STATE.md [18]）

## 方針

Figma のデザインは固定幅カンバス（点）であり、実装は連続する幅（線）である。本節は「点をどの区分に割り当て、点と点の間をどう補間するか」を規則化する。Web開発プレイブック `rules/breakpoints.md`（実在パス: `C:\AI\web-development\rules\breakpoints.md`。2026-06-27 制定の恒久ルール）を**上位規則として継承**する。

原則: 補間はエージェントの美観判断ではなく本節の既定規則で行い、既定で解けないもの（§4 のリスト該当）はデザイナー確認へ回す。

根拠の凡例は Q-01 と同じ:【公式】【実測:MyBrain】【実測:スキーマ】【仮説】

## 1. ブレークポイントの決め方

- 標準区分【実測:MyBrain breakpoints.md】（幅の範囲は ASCII ハイフン `-` で表記統一する。本仕様の規定）:
  - PC: 1272px 以上（`@media only screen and (min-width: 1272px)`）
  - タブレット: 768-1271px
  - SP: 767px 以下
- デザインカンバスの標準幅【実測:MyBrain breakpoints.md】: PC = 1440px、SP = 375px。個別指示や Figma 上のフレーム幅が異なる場合はそのフレームを優先する。
- **カンバス幅はデザイン基準幅であって、ブレークポイントではない**（1440px のデザインを 1272px 以上の全幅に適用する）。
- Figma に標準外の幅のフレーム（例: 768px のタブレットデザイン）がある場合は、どの区分に割り当てるかをデザイナーに確認し、結果を案件側 `MyBrain/rules/` に記録する。フレームの存在を無視して標準区分だけで実装しない。

## 2. デザインに無い中間幅の補間規則（既定）

デザインが存在する幅（基準幅）ではデザイン実値をそのまま使い、無い幅は次の規則で補間する。

### 2-1. 区分内の補間

| 幅の範囲 | 規則 |
|---|---|
| 基準幅より広い（1441px 以上） | コンテンツ幅は `max-width: 基準幅のコンテンツ幅` で固定し中央寄せ。背景（色・帯・画像）だけを全幅へ伸ばす。ヒーロー等の全幅画像は `object-fit: cover` で拡大し、切れてよいかは §4-7 の確認事項 |
| PC区分内・基準幅未満（1272-1439px） | コンテナ幅を可変（`max-width` + 左右 padding 固定）にし、内部は Q-03 の flex 構造で自然に詰める。フォント・余白の固定値は変更しない |
| タブレット区分（768-1271px） | 専用デザインが無い場合の既定: PCレイアウト構造を維持したままコンテナ可変で縮める。構造調整の条件と手順は 2-1-1 |
| SP区分内（320-767px、基準 375px） | 375px の実値を基準にコンテナ可変。320px（§4-3 の最小サポート幅の既定値）まではみ出し・横スクロールが出ないことを検証条件とする |

#### 2-1-1. タブレット区分の構造調整規則（専用デザインが無い場合）

- **調整のトリガー**: 検証幅（§2-3）の実ブラウザ検証で、①横スクロールの発生 ②要素同士の重なり ③テキスト/画像のコンテナからのはみ出し、のいずれかが機械検出された場合**のみ**調整する。見た目の好みによる調整はしない。
- **調整の順序**（上から順に試し、解消した時点で止める）:
  1. Fill 要素の伸縮に任せる（調整なしで解消するか再確認）
  2. カラム数を1段階減らす（4→3→2→1。グリッド/カード列が対象）
  3. 横並び（flex-direction: row）を縦積み（column）へ切り替える
  4. それでも解消しない場合は SP レイアウト構造を適用する
- フォントサイズ・余白の縮小は調整手段にしない（Figma実値との照合可能性を保つため。縮小が必要に見える場合は §4-6 のデザイナー確認へ）。
- 実施した調整（対象要素・適用した段階・切替幅）は実装メモに記録し、§4-1 の確認事項としてデザイナー/kazu に報告する。

### 2-2. 何を固定し、何を可変にするか

- 可変にする: コンテナ幅、カラムの伸縮（Q-03 の Fill）、画像の表示幅（`max-width: 100%`）。
- 固定のまま: フォントサイズ、行間、余白・gap のデザイン実値、線の太さ（px【実測:web-development corrections.md 2026-07-07】）、ロゴ・アイコンの寸法。
- `vw` 連動のフォント/余白スケーリング（fluid typography）は**既定では使わない**。案件側規約に明示がある場合のみ使う（本仕様の規定。理由: Figma実値との照合可能性を保つため）。
- 同一HTMLを CSS で調整する。PC用/SP用の HTML 重複と `display: none` 切替は禁止。例外は意味・アクセシビリティ・パフォーマンス上の理由がある場合のみで、理由をコードか実装メモに残す【実測:MyBrain breakpoints.md 禁止事項】。
- `figma-gate preflight` は `scope.responsiveHtml.sourceFiles` を走査し、同じ本文を持つ `*-pc` / `*-sp` 要素を検出した時点で失敗する。例外は `sourceFile`・`baseClass`・具体的な理由をmanifestへ記録した場合だけ許可する。視覚差分や改行の調整は例外理由にならない。

### 2-3. 検証幅

補間結果は次の幅で実ブラウザ検証する（検証手順自体は Q-09）: 基準幅（1440 / 375）、各区分の境界（1272 / 1271 / 768 / 767）、最小幅（320）。境界幅では左右両側（±1px）を確認する。

- 最小幅 320px は上位規則 `breakpoints.md` に規定が無い**本仕様の追加規定**（現行 iPhone SE 世代の最小級ビューポートを想定した既定値。【仮説】であり、§4-3 のデザイナー確認と kazu の確定承認で案件ごとに見直してよい）。

## 3. 順序の入れ替え

- PC とSP でコンテンツの視覚順序が異なるデザインは、HTML は文書として自然な順序（原則 SP の順序）で書き、視覚順序の差は flex の `order` / grid 配置で吸収する（本仕様の規定）。
- `order` を使った場合、DOM 順序と視覚順序の乖離がアクセシビリティ（フォーカス順）に影響するため、キーボード操作の確認を Q-09 の未自動化項目に含める。

## 4. デザイナーへ確認すべき事項（チェックリスト）

案件開始時（または該当が判明した時点）に確認し、回答を案件側 `MyBrain/rules/` に記録する。未回答の項目は既定規則（§2）で暫定実装し、暫定である旨を報告に明記する。

1. タブレット区分の扱い: PC構造の縮小か、SP構造の拡大か、専用デザインを作るか（§2-1 の既定は PC縮小）
2. 基準幅より広い画面での背景・全幅要素の伸ばし方（色・画像・パターンごと）
3. 最小サポート幅（既定 320px）と、最大幅の上限（コンテンツを止める幅）
4. ヘッダー/ナビの切替点（ハンバーガー化する幅。区分境界と一致させてよいか）
5. 中間幅での見出し・リード文の改行位置の許容（Figma の改行を `<br>` で固定するか、自然折返しに任せるか — Q-04 §4 既知例3）
6. フォントサイズの縮小可否（区分内でデザイン実値を維持できない場合）
7. 画像のトリミング許容（`object-fit: cover` でどこが切れてよいか。フォーカルポイントの指定）
8. Figma に無い状態（テキストが極端に長い/短い場合、項目数が増減する場合）の挙動
