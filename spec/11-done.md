# 11. 「正確」の完成判定（Q-11）

- 設問: 「正確」の完成判定をどう定義するか？
- 状態: 合格（kazu の確定承認待ち。批評記録は STATE.md [28]）

## 方針

「正確」を「**spec 化された全項目が数値基準内で PASS し、機械照合できない項目が未確認リストとして明示され、人間レビューで承認された状態**」と定義する。機械 PASS だけでも、人間の目視だけでも「完成」としない。「見た目は大体合っている」「主要要素は合っている」を判定根拠にすることを禁止する【実測:MyBrain figma-spec-pipeline.md 停止条件】。

根拠の凡例は Q-01 と同じ:【公式】【実測:MyBrain】【実測:スキーマ】【仮説】

## 1. 一致レベルの線引き

| レベル | 対象 | 判定 |
|---|---|---|
| **完全一致**（差分ゼロを要求） | computed style 値（color / background / font-size / 換算後の line-height・letter-spacing / radius 等）、文言・改行位置・行数（Q-07 §4-5 の確認結果に従う）、DOM 全件対応表（欠落・余計な要素ゼロ）、アセットの実体（形式・透過・解像度） | 機械判定（Q-09 層2） |
| **数値許容**（閾値内を合格とする） | bounding box の座標・寸法、スクリーンショット差分率、Scale 換算の丸め誤差 | 機械判定（§2 の数値基準） |
| **一致を求めない**（Figma が正解を持たない領域） | デザインに無い中間幅の補間結果（Q-07）、既定値を適用したインタラクション（Q-08 §2-2）、実機 Safari / iOS のレンダリング、モーションの質感 | 人間レビュー（§3）。未確認リスト・暫定実装一覧として必ず明示 |

- ピクセル一致（スクリーンショットの完全一致）は**要求しない**。理由: Figma とブラウザのレンダリング差（Q-04 §4）とアンチエイリアスにより、正しい実装でも差分ゼロにならないため。ピクセル比較は Q-09 §2 の差分率閾値で判定する。
- Figma データ側の矛盾（固定高さと中身合計の不一致等）を検出した場合は、どちらに合わせたかを根拠つきで記録した上で PASS 扱いにできる【実測:MyBrain figma-spec-pipeline.md】。

## 2. 許容差分の数値基準（一覧）

| 項目 | 基準 | 出典 |
|---|---|---|
| bounding box（left / topInSection / width / height） | 誤差 ±1.5px 以内 | 【実測:MyBrain figma-spec-pipeline.md】 |
| computed style | 完全一致（誤差 0） | 同上 |
| 文言・改行・行数 | 完全一致 | Q-09 §3 |
| body scrollWidth（横はみ出し） | 0px（検証幅: 1440 / 1272 / 1271 / 768 / 767 / 375 / 320 の全幅。Q-07 §2-3 の一覧を固定転記） | 【実測:MyBrain figma-spec-pipeline.md】＋Q-07 |
| スクショ差分率（非テキスト要素） | <= 1.0% | Q-09 §2-3 |
| スクショ差分率（テキスト含む要素） | <= 3.0% | Q-09 §2-3 |
| スクショ差分率（セクション全体） | <= 2.0% | Q-09 §2-3 |
| Scale 換算の丸め誤差 | **bounding box の許容誤差に加算する**（該当要素のみ 許容 = ±1.5px + 親寸法 x 0.005%。スクショ差分率には加算しない） | Q-03 §3-2 |
| lint（単位規約・禁止パターン） | エラー 0 | 【実測:MyBrain figma-spec-pipeline.md】 |

| 色コントラスト（機械判定対象のみ。境界は Q-13 §3-3） | 通常テキスト 4.5:1 以上 / 大テキスト 3:1 以上 / UI 3:1 以上 | Q-13 §1（WCAG 2.1 1.4.3 / 1.4.11） |
| キーボード走査 | 到達性・DOM順一致・フォーカストラップ/Esc・フォーカス可視の4条件 PASS（可視差分なし要素 0 件） | Q-13 §3-4 |

数値基準の変更は kazu の承認事項とし、変更履歴を本節に残す。

## 3. 人間レビューで見る項目（機械照合できないもの）

機械判定が全 PASS した後、次を人間（kazu / デザイナー）がレビューする。レビュー依頼には Q-09 §4-6 の証跡3点＋未確認リスト＋既定値適用一覧＋暫定実装一覧を添付する。

1. **デザイン意図**: 余白のリズム・強弱・視線誘導が意図どおりか（数値が合っていても意図とズレる場合の最終判断）
2. **中間幅の補間結果**: Q-07 §2-1-1 で構造調整した箇所、タブレット幅の見え方
3. **既定値を適用したインタラクション**: Q-08 §2-2 の適用一覧（hover・トランジション）
4. **実機確認**: Safari / iOS Safari の表示・操作（Web開発プレイブック `rules/browser-compatibility.md` 参照）
5. **文言・リンク**: 誤字・ダミーテキスト残り・リンク先の正しさ（CMS 由来の可変文言を含む）
6. **運用品質**: ブラウザコンソールにエラーが無いこと（W3C検証は `C:\AI\web-development\rules\w3c-validation.md`、キーボード走査は §2 の機械判定に従う — Q-13）
7. **アクセシビリティの人間レビュー**: Q-13 §1 の人間列に従う — alt / aria-label の**文言**妥当性、見出し階層の意味妥当性、order による視覚順と DOM 順の乖離の許容判断、画像・グラデ背景上のコントラスト目視、コントラスト未達リスト（Q-13 §2）の採否
8. **Figmaデータ側の矛盾への対処**: §1 で記録した「どちらに合わせたか」の判断の妥当性

## 4. 完成判定のフロー

1. **機械判定**: Q-09 の3層（lint エラー0 / CDP照合 全PASS / スクショ差分率 閾値内）がすべて合格
2. **報告**: 上位規則の報告テンプレート【実測:MyBrain figma-spec-pipeline.md】に従い、①spec パス ②lint 結果（W3C 含む）③verify 全PASS ログ＋スクショ証跡 ④アクセシビリティ機械検査の結果（axe-core 結果・コントラスト算出表・キーボード走査ログ — Q-13 §1）⑤未確認リスト・既定値適用一覧・暫定実装一覧・コントラスト人間判定リスト を添付して報告する。機械判定に FAIL が残る状態で「完了」と報告しない
3. **人間レビュー**: §3 の8項目。指摘があれば Q-10 の順序で修正し、1へ戻る
4. **完成**: 人間レビューの承認をもって「完成」とする。公開を伴う場合は、公開 URL での再検証（Q-09 §4-5）まで完了してから公開完了と報告する【実測:MyBrain corrections.md 2026-07-11】

## 5. 合否基準との対応

- ピクセル一致を求める範囲と許容する範囲の線引き: §1
- 許容差分の数値基準: §2
- 人間レビューで見る項目: §3
