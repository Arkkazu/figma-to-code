# 06. コンポーネントの対応付け（Q-06）

- 設問: Figmaコンポーネントと既存コードコンポーネントをどう対応付けるか？
- 状態: 合格（kazu の確定承認待ち。批評記録は STATE.md [16]）

## 方針

Figmaコンポーネント ⇔ コードコンポーネントの対応の**正はマッピング表**とする。Code Connect が使える案件は Code Connect のマップを正とし、使えない案件（既定）は案件側 `MyBrain/rules/component-map.md` を正とする。マップに無いものをエージェントの記憶や見た目の類似だけで対応付けない。

根拠の凡例は Q-01 と同じ:【公式】【実測:MyBrain】【実測:スキーマ】【仮説】

## 1. 前提確認（案件開始時に1回）

- Code Connect の利用条件: 「**Organization・Enterprise プランの Dev または Full シート**で利用可能」【公式・出典1】。案件の Figma プラン・シートを kazu に確認し、満たさない場合は §4（手動マップ運用）に確定する。
- Code Connect 利用可の場合も、コード側にマッピング（CLI のテンプレートファイル等【公式・出典1】）が未整備なら、整備されるまで §4 で運用し、§3-3 の登録で段階的に移行する。

## 2. 再利用か新規作成かの判断フロー（インスタンスごと）

1. **種別確認**: `get_metadata` で対象ノードの type を確認する。COMPONENT / INSTANCE でなければ通常実装（Q-03）へ。
2. **マッピング照会**: Code Connect 利用時は `get_code_connect_map`、非利用時は案件側 `MyBrain/rules/component-map.md` を照会する。
3. **マッピングあり** → 既存コードコンポーネントを再利用する。variant・プロパティは `get_design_context` の variant 情報から写像する。既存実装とFigmaの見た目に数値差分がある場合は勝手に上書きせず、「デザイン更新か実装の乖離か」をデザイナー/kazu に確認する。
4. **マッピングなし** → 既存コードを検索（コンポーネント名・DOM構造・見た目）し、次の基準で判断する:
   - **再利用**（そのまま使う）: DOM構造が同一で、差分が文言・画像・リンク先のみ。
   - **拡張**（variant / modifier を追加）: DOM構造が同一で、スタイル差分が modifier 1つで表現できる。拡張前に、既存の全使用箇所に影響が無いことをビルド後CSSで確認する。
   - **新規作成**: 上記に該当しない。見た目が似ていても余白・色・構造の数値差分がある場合は「同一視」しない（意図的な差か旧版かをデザイナー確認事項として起票し、回答までは新規として実装する）。
5. **新規作成の規約**: 命名・構造は案件規約とWeb開発プレイブック `rules/scss.md`（BEM ネスト・二重定義禁止）に従う。作成前に、共通CSSが全ページへ配っている既存クラス名と衝突しないことを確認する【実測:web-development mistakes.md 2026-06-25（2）クラス名衝突の既知事例】。
6. **マップ更新**: 再利用・拡張・新規のいずれでも、結果をマッピング表（§3 / §4）に反映する。

## 3. Code Connect を使う場合の手順

1. **案件開始時・実装対象ごと**: `get_code_connect_map` は `nodeId` + `fileKey` が必須で、指定ノードを起点とした `{nodeId: {codeConnectSrc, codeConnectName}}` の対応を返す（ファイル全体を一括取得する手段は無い）【実測:スキーマ】。したがって照会は実装対象単位で行う: 実装するページ/セクションのルート nodeId を起点に呼び、返却された対応を案件のマップ一覧（§4 の表と同形式）へ蓄積する。複数言語のマッピングがある場合は `codeConnectLabel` で案件の実装言語を指定する【実測:スキーマ】。
2. **実装中**: マップ済みインスタンスは返却されたコンポーネント参照（codeConnectSrc / codeConnectName）を使い、ゼロから書き直さない。ネストしたコンポーネントの確認範囲は**照会した起点ノードの返却に含まれる分まで**とし、返却に無い深い階層は、その子コンポーネントを実装する番になったときに当該ノードを起点に再照会する（一括の深掘りをしない。本仕様の規定）。
3. **実装後**: 新規作成したコンポーネントは `add_code_connect_map` でマップに登録する。**Figmaへの書き込みになるため、登録実行は kazu の承認後**（本仕様の規定）。
4. フレームワーク・言語の指定は案件の実装言語に合わせる（`get_code_connect_map` はフレームワーク/言語の絞り込みに対応【公式・出典2】）。

## 4. Code Connect を使わない場合の手順（既定）

- 案件側 `MyBrain/rules/component-map.md` をマッピング表として維持する。**ファイルが未作成の案件では、最初のコンポーネント実装前に下記書式のヘッダのみの空表を作成し、作成した旨を案件の作業記録（daily / STATE 相当）に残す**（本仕様の規定）。書式（1コンポーネント1行）:

```
| Figmaコンポーネント名 | fileKey / nodeId | コード側の実体（パス・クラス名） | 状態（実装済み/暫定） | 備考 |
```

- 実装エージェントは、コンポーネントらしき要素（繰り返し・カード・ボタン等）に触れる前に必ずこの表を参照する。
- 再利用・拡張・新規のいずれの場合も、同じイテレーション内で表を更新し、完了報告に表の差分を添付する（更新漏れの検出手段。本仕様の規定）。
- WordPress 案件では「コードコンポーネント」= テンプレートパーツ（`template-parts/` 等）＋対応する SCSS ブロックを指す。表のコード側にはテンプレートパーツのパスと ルートクラス名の両方を書く。

## 5. 合否基準との対応

- 既存コンポーネントを再利用するか新規作成するかの判断フロー: §2
- Code Connect を使う場合の手順: §3
- 使わない場合の手順: §4（利用可否の判定は §1）
